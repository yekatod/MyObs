# 🩷 2.5. SOLID — O

## Open/Closed Principle

> **Класс открыт для расширения, но закрыт для модификации.**

### Темы

- extension points
- polymorphism
- abstraction
- strategy pattern
- switch/if explosion
- расширение без изменения существующего кода

}

}

# 🩷 2.6. SOLID — L

## Liskov Substitution Principle

> **Объект производного типа должен корректно заменять объект базового типа.**

### Темы

- контракт базового типа
- поведение наследника
- preconditions
- postconditions
- invariants
- нарушение контрактов
- классический пример Rectangle / Square
- исключения как нарушение LSP
- `NotSupportedException`

Очень важно:

**LSP — не про то, что «наследник должен иметь все методы родителя».**

Это про **сохранение поведенческого контракта**.

---

# 🩷 2.7. SOLID — I

## Interface Segregation Principle

> **Клиент не должен зависеть от методов, которые ему не нужны.**

### Темы

- fat interface
- role interfaces
- интерфейсы для конкретных клиентов
- маленькие интерфейсы
- ISP + DI
- ISP + mocking/testing

Плохой пример:

interface IWorker

{

    Work();

    Eat();

    Sleep();

}

И:

Robot : IWorker

приходится реализовывать:

Eat();

Sleep();

# 🩷 2.8. SOLID — D

## Dependency Inversion Principle

> **Модули верхнего уровня не должны зависеть от модулей нижнего уровня. Оба должны зависеть от абстракций.**

### Темы

- high-level / low-level modules
- abstraction
- dependency inversion
- dependency injection
- constructor injection
- IoC
- DIP vs DI
- почему `new` внутри класса создаёт жёсткую зависимость
- тестируемость

Например:

public class OrderService

{

    private readonly SqlOrderRepository _repository;

  

    public OrderService()

    {

        _repository = new SqlOrderRepository();

    }

}

vs

public class OrderService

{

    private readonly IOrderRepository _repository;

  

    public OrderService(IOrderRepository repository)

    {

        _repository = repository;

    }

}

# 🩷 2.11. YAGNI

## You Aren't Gonna Need It

### Темы

- проектирование под текущие требования
- overengineering
- speculative features
- premature abstraction
- premature optimization
- баланс между extensibility и complexity

Очень хороший вопрос:

> **Нужно ли создавать абстракцию сейчас, если пока существует только одна реализация?**

Ответ:

> Зависит от причины. Если абстракция нужна для инверсии зависимости, тестирования или архитектурной границы — возможно, да. Если она создана «на всякий случай» — скорее всего, YAGNI.

> Класс должен иметь хорошо сфокусированную ответственность.

#### Polymorphism

> Разное поведение по типу объекта можно выразить через полиморфизм.

#### Pure Fabrication

> Иногда создаём технический класс, чтобы не перегружать domain entity.

# 🩷 2.13. Law of Demeter

> **Не разговаривай с друзьями друзей.**

Типичный пример:

order.Customer.Address.City.Name

Это подозрительно.

### Темы

- loose coupling
- train wreck
- цепочки вызовов
- encapsulation
- Tell, Don't Ask
- нарушение инкапсуляции

Вместо:

order.Customer.Address.City.Name

может появиться:

order.GetCustomerCityName();

или более осмысленная доменная операция.

Но здесь важно не превратить Law of Demeter в:

> «Никогда нельзя писать больше одной точки».

Это **не так**.

# 🩷 2.15. Singleton

Тут не нужно просто знать:

> «Singleton — паттерн, который создаёт один объект».

Нужно понимать **почему его часто считают опасным**.

### Темы

- Singleton pattern
- global state
- скрытые зависимости
- lifetime
- thread safety
- тестирование
- mutable Singleton
- Singleton через DI
- когда Singleton оправдан

Особенно:

public static MyService Instance { get; }

vs

services.AddSingleton<IMyService, MyService>();

Это **не одно и то же с точки зрения архитектуры приложения**.
